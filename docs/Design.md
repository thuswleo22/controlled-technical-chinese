# CTC 的设计取舍

## 目标

CTC 要让读者据同一份技术文档做出一致的操作判断。它借鉴 ASD-STE100 对术语、操作句和可审查规则的思路。中文需要处理承前省略、词类兼用、指代与语序。规则围绕具体信息设计，以便编辑说明每次修改依据什么。

[ASD-STE100 官方资料](https://www.asd-ste100.org/)

## 六类规则

| 类别 | 控制的对象 | 当前自动检查 |
| --- | --- | --- |
| LEX | 词义与谓词写法 | 复制动作词、编码谓词。 |
| REF | 执行者和指代对象 | 受控步骤字段、动作或措施中的悬空指代。 |
| LOG | 条件组合与分组 | 混合连接词的范围、圆括号配对。 |
| MOD | 义务、建议、许可、能力和禁止 | 已标注强度的条款及其主句标记。 |
| QNT | 数量区间 | 同量同单位上下界的空区间。 |
| DOC | 操作信息的呈现 | 警告中的措施与后果字段。 |

每条诊断只归一个编号。Markdown 段落、行号、代码和引用由共用的输入处理负责。术语词典用于核对具体义项。检查器按编号执行正式规则。

## 合并初期方案

早期方案包括 Carbon 提出的指代、条件、阈值、警告和工具接口设计，以及对语料、义项、条件真值和角色的已有实验。合并时用具体工程含义检查每条建议，并用正反例限定实现范围。

- 将指代约束用在需要动作对象的字段。普通说明可以承前省略可明确推断的成分。
- 按业务角色写步骤字段。原文有处置句、被动句或多重限定时，核对结构是否会遮蔽角色或条件。
- 将权限、能力、义务、建议和禁止各自表达。改写时按原始规则确定强度。
- 用真值表区分包含式「或」和异或。限定数量范围时核对单位和端点。保留测量中的近似和不确定性。
- 将句长和「的」字密度用作编辑观察。拆句时保留对象、工具、条件和时序。
- 保留行号、规则编号、JSON 诊断及规范自举检查。用可运行的公开报告支持检测行为。

## 业务含义核验

检查器可以强制表达分组。工程资料或测试用来决定如何分组。角色、阈值、模态和警告措施也应由来源材料确定。把每个关键动作和条件映射回原文。遇到含糊的业务规则时，记录可行的解释并请负责人确认。
